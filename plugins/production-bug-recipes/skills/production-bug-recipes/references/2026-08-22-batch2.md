## UPDATE TO Recipe #8 — The "Daily popup" day boundary bug was mis-fixed (added Aug 22 2026)

The original Recipe #8 (which I wrote earlier this same session) suggested "convert UTC → local-day" as the fix:

```ts
// WRONG — does TZ conversion on only ONE side of the comparison
const todayLocal = (() => {
  const d = new Date()
  const y = d.getFullYear()              // ← local year
  // ...
})()
const streakLastAsLocal = (() => {
  const utcDate = s.split('T')[0]  // "2026-08-22" (UTC)
  const d = new Date(utcDate + 'T00:00:00Z')
  d.getDate()  // returns LOCAL date — "2026-08-21" in Eastern time
})()
const hasClaimedToday = streakLastAsLocal != null && streakLastAsLocal === todayLocal
```

**This was wrong.** The asymmetry is exactly what causes the bug. The user (Eastern time, UTC-4) clicked Collect at 11 PM Eastern on Aug 21; SQL stamped `streak_last_date = 2026-08-22` UTC. Client converted to local-day = `2026-08-21`. `todayLocal` at 11:30 PM Eastern was also `2026-08-21`. They matched — popup stayed closed. 30 min later at midnight Eastern (= Aug 22 04:30 UTC), `todayLocal` flipped to `2026-08-22`. The DB column was unchanged. They no longer matched — popup re-fired.

The correct fix is UTC-to-UTC, no conversion on either side:

```ts
const todayUtc = (() => {
  const d = new Date()
  const y = d.getUTCFullYear()
  const m = String(d.getUTCMonth() + 1).padStart(2, '0')
  const day = String(d.getUTCDate()).padStart(2, '0')
  return `${y}-${m}-${day}`
})()
const streakLastUtc = (() => {
  const s = profile?.streakLastDate
  if (!s) return null
  return s.split('T')[0]        // truncate only, no TZ conversion
})()
const hasClaimedToday = streakLastUtc != null && streakLastUtc === todayUtc
```

The lesson: **never mix UTC and local timezones in the same comparison.** Either everything is UTC (preferred when the server is UTC) or everything is local. The original recipe said "Always compare in the user's local timezone" — that's the wrong rule. The right rule is "always compare in the same timezone as the server." Since `streak_log` is UTC-anchored and `streak_last_date` is stored as a UTC DATE, the client should be UTC-anchored too.

When updating SKILL.md, replace the body of Recipe #8 with the UTC-to-UTC version and add this as a footnote.

## NEW Recipe #23 — TraderHubTab "save changes doesn't work" — compound bug from three Recipe #15 / #20 layered failures (added Aug 22 2026)

**Symptom:** admin opens the customers/Manage drawer for a trader (e.g. self-row in the demo), edits the Display name field, clicks Save changes → nothing happens. No toast, no error, no spinner stops. The DB row's display_name is unchanged. Subsequent clicks do nothing.

**Root cause — three layers stacked:**

1. **The handleSave function uses `adminFetch`** which (before this session's fix) called `supabase.auth.getSession()` and acquired the `navigator.locks` lock. When the lock timed out, the Bearer header was missing → server returned 401 → `if (!res.ok || !data.ok) throw new Error(...)` → `catch (e) → setFeedback({ ok: false, message: e.message })`. **The error feedback WAS set**, but it scrolled off-screen or the admin didn't notice.

2. **The `loadingProfile` useEffect had `.finally(() => setLoadingProfile(false))` which doesn't run if `adminFetch` throws synchronously** (e.g. malformed localStorage JSON). If the initial profile load failed, `loadingProfile` stayed `true` forever. The Save button has `disabled={saving || loadingProfile}` — when `loadingProfile=true`, the button is permanently disabled, no amount of clicking helps.

3. **The fix to (1) landed first** (`adminFetch` rewriting the lockManager path). After a hard refresh the lockManager goes away. **The fix to (2) didn't land in the same commit** so the user still sees "Save changes does nothing" because `loadingProfile` is stuck at true from a sync throw in `adminFetch` during the initial profile load.

**The fix — defensive loadingProfile handling in TraderHubTab:**

```tsx
// BEFORE (Recipe #15's lockManager fix landed but didn't cover sync throws)
useEffect(() => {
  if (!isTrader || !userId) return;
  setLoadingProfile(true);
  adminFetch(`/api/admin/trader-profile/${userId}`)
      .then((r) => (r.ok ? r.json() : Promise.reject(r)))
      .then((data) => {
        if (data.profile) {
          setProfile(data.profile);
          setForm({ ... });
        }
      })
      .catch(() => { /* profile may not exist yet — that's fine */ })
      .finally(() => setLoadingProfile(false));
}, [isTrader, userId]);

// AFTER (companion fix to the lockManager path)
useEffect(() => {
  if (!isTrader || !userId) return;
  let cancelled = false;
  setLoadingProfile(true);
  const reset = () => { if (!cancelled) setLoadingProfile(false); }
  adminFetch(`/api/admin/trader-profile/${userId}`)
      .then((r) => {
        console.log('[TraderHubTab] profile load status:', r.status);
        return r.ok ? r.json() : Promise.reject(new Error(`HTTP ${r.status}`));
      })
      .then((data) => {
        if (cancelled) return;
        if (data.profile) {
          setProfile(data.profile);
          setForm({ ... });
        }
      })
      .catch((err) => {
        console.warn('[TraderHubTab] profile load failed:', err?.message || err);
      })
      .finally(reset);
  return () => { cancelled = true; };
}, [isTrader, userId]);

// AND in handleSave — add console.log so the user can diagnose in DevTools:
const handleSave = async () => {
  if (!userId) return;
  setSaving(true);
  setFeedback(null);
  try {
    const payload = { ... };
    console.log('[TraderHubTab] save click — payload:', payload);
    const res = await adminFetch('/api/admin/enable-trader', { ... });
    console.log('[TraderHubTab] PATCH status:', res.status);
    const data = await res.json();
    console.log('[TraderHubTab] PATCH response:', data);
    if (!res.ok || !data.ok) {
      throw new Error(data?.error || `HTTP ${res.status}`);
    }
    setProfile(data.profile || profile);
    setFeedback({ ok: true, message: 'Trader profile updated.' });
    await onChange();
  } catch (e) {
    console.error('[TraderHubTab] save failed:', e?.message || e);
    setFeedback({ ok: false, message: e?.message || 'Save failed' });
  } finally {
    setSaving(false);
  }
};
```

**The diagnostic flow when the user reports "Save doesn't work":**

1. Ask the user to open Safari → Settings → Advanced → Web Inspector → Connect to iPhone → reload the page.
2. In the console, look for these logs (added by the fix above):
   - `[TraderHubTab] profile load status: <200|401|...>` — tells you whether the profile loaded at all
   - `[TraderHubTab] profile loaded: Test Trader Julyan` — confirms the form was populated
   - `[TraderHubTab] save click — payload: {...}` — confirms the click handler fired and what was sent
   - `[TraderHubTab] PATCH status: 401` — auth failed (lockManager or expired token)
   - `[TraderHubTab] save failed: ...` — surface the real error message
3. The console log sequence tells you exactly which step broke. Before this fix, the failure was silent.

**The broader lesson — when fixing Recipe #15 (lockManager), audit every component that uses `loadingProfile` / `saving` / `submitting` flags with `.finally()` reset, because they all have the same sync-throw window:**

```bash
rg -n "setLoading\(true\)" src/ | grep -v "useState"
# Walk each match — does it have a corresponding `.finally()` that's guaranteed to run?
```

If not, refactor to the named-reset-function pattern. Save yourself the "the user says Save doesn't work after I fixed the lockManager" round.

## NEW Recipe #24 — The admin "Trader Access" toggle in the Access tab (added Aug 22 2026)

**Pattern:** a lightweight admin endpoint that flips a single boolean flag, with a comprehensive e2e test that exercises every error path. The shape of this endpoint is reusable for any "grant/revoke permission" toggle.

**The endpoint — `POST /api/admin/set-trader-flag`:**

```ts
// Body: { user_id, is_trader: boolean }
// Auth: admin only
// Returns: { ok, publicUser: { id, is_trader, trader_status, trader_since }, message }
//
// Behavior:
//   - Flips user_accounts.is_trader and trader_status atomically
//   - Stamps trader_since ONLY on the FIRST grant transition (when DB row
//     has no trader_since yet). Subsequent revoke→re-grant cycles leave
//     the original promotion date intact.
//   - Honors notify_signals opt-outs for the push fan-out (when present)
//   - Returns 404 for unknown user_id, 403 for non-admin, 401 for no bearer,
//     400 for missing/invalid fields
```

**The bug we caught while writing the e2e test:** the first version gated `trader_since` updates on `!existingPU.is_trader`. But after a revoke, `existingPU.is_trader = false`, so a re-grant looked like a fresh transition and re-stamped `trader_since` to the new time. The visible bug: an admin revokes a trader, then re-grants them, then the UI says "active trader since just now" — losing the original promotion date.

```ts
// WRONG — re-stamps trader_since on every re-grant
if (body.is_trader && !existingPU.is_trader) {
    update.trader_since = new Date().toISOString()
}

// CORRECT — only stamp on the first grant
if (body.is_trader && !existingPU.trader_since) {
    update.trader_since = new Date().toISOString()
}
```

**The 11-step e2e test pattern** (any new "flip a boolean" admin endpoint should run this same shape):

```bash
1. Auth as admin via magic link → JWT
2. Find a non-trader user (target for the toggle)
3. Toggle ON → assert 200, is_trader=true, trader_status='active', trader_since set
4. Read DB → assert persistence
5. Toggle OFF → assert 200, is_trader=false, trader_status='deactivated', trader_since preserved
6. Toggle ON again → assert trader_since UNCHANGED (preservation across revoke cycles)
7. Non-admin JWT → assert 403 Forbidden
8. Missing user_id → assert 400 with 'user_id (auth.users.id) is required'
9. Non-boolean is_trader ('yes') → assert 400 with 'is_trader must be a boolean'
10. Unknown user_id ('00000000-...') → assert 404 with 'User not found'
11. No bearer → assert 401 with 'No token'
```

After tests pass: cleanup by restoring the target user to their original state via the same endpoint. Document the `trader_since` preservation behavior in code comments because it's not obvious from the API shape.

**The UI gate on the client — visible to admins only:**

```tsx
// In src/app/dashboard/customers/AdminUsersPanel.tsx
{canSendSignal && pendingTrader && (
  <div className="admin-division-toggle enabled" style={{ '--div-color': '#a855f7' }}>
    <Radio size={18} />  {/* violet accent */}
    <strong>Trader Access</strong>
    <span>Active trader · can send signals</span>
  </div>
)}
```

The toggle is added between the Divisions block and the Partner block in the Access tab. Clicking it stages `pendingTrader` (local state). Clicking Save fires `adminFetch('/api/admin/set-trader-flag', ...)` alongside the existing division toggle saves — `Promise.all` dispatches them in parallel.

**Why this exists alongside the TraderHubTab's activate flow:** TraderHubTab still owns display_name/slug/bio setup; this Access tab toggle is the simpler grant/revoke switch. Two surfaces for two different admin workflows: "set up a new trader" (TraderHubTab) vs. "flip the permission" (Access tab).
